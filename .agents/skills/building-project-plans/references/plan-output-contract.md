# Canonical Plan Output Contract

Every plan generated by `building-project-plans` must strictly follow the canonical external structure. Internal normalization, risk matrices, and dependency graphs support this output but must not replace or disrupt this structure.

---

## Output Architecture Overview

```text
<Project Name> — Complete Delivery Plan

A. Planning / Architecture Decisions

B. Task Inventory
   W0 — [Gate/Discovery Workstream, if required]
   W1 — [Domain Workstream 1]
   W2 — [Domain Workstream 2]
   ...
   Wn — [Hardening / Cross-Domain Verification Workstream]

C. Sequencing

Optional: PM Proposals
```

The output order is fixed:
1. **Section A** must appear first. Upstream decisions govern all downstream work.
2. **Section B** follows Section A. Every task is assigned to a workstream and numbered globally.
3. **Section C** follows Section B. It translates dependencies into executable sequencing, gates, and parallel execution branches.
4. **Optional PM Proposals** appear at the very end when project management tool integration is requested.

---

## Destination & Persistence Contract: `/docs/plan/`

When planning completes, the plan artifacts must be persisted directly into the project's `/docs/plan/` folder:

```text
<Project Root>/
└── docs/
    └── plan/
        ├── plan.md       # Complete Delivery Plan (Overview, Section A Decisions, Section C Sequencing)
        └── tasks.md      # Actionable Task Inventory (Section B: W0...Wn, Tasks 1..N with acceptance criteria)
```

### File Responsibilities:
- **`docs/plan/plan.md`**: Contains the strategic delivery blueprint:
  - Project Title & Classification Overview
  - **A. Planning / Architecture Decisions** (Material decisions, rationale, constraints, affected workstreams)
  - **C. Sequencing** (Hard gates, parallelization branches, critical path)
  - **Optional: PM Proposals** (Normalized tickets for Jira/Linear/GitHub Issues)
  - Summary link to `tasks.md`
- **`docs/plan/tasks.md`**: Contains the tactical execution inventory:
  - **B. Task Inventory** organized by workstreams (`W0...Wn`)
  - Globally continuous tasks (`1..N`) with action titles, deliverables, programmatic acceptance criteria, verification commands, and explicit dependencies/blocks.

*Note*: For multi-project programs or versioned initiatives, use `docs/plan/<initiative>-plan.md` and `docs/plan/<initiative>-tasks.md` with default symlinks or copies at `docs/plan/plan.md` and `docs/plan/tasks.md`.

## Section A: Planning / Architecture Decisions

Section A documents choices that materially affect system architecture, interfaces, data integrity, security, migration, delivery order, or operability.

### Inclusion Criteria
A decision belongs in Section A if an unresolved choice could:
- Force rework across multiple workstreams if changed later.
- Introduce irreversible data model or persistence changes.
- Alter security, authorization, or trust boundaries.
- Break backward compatibility with existing clients or consumers.
- Define public integration contracts or operational models.

Do **not** document trivial implementation details (e.g., choice of local variable names, minor helper functions, routine syntax preferences).

### Decision Format Contract
Each material decision must follow this structure:

```markdown
### Decision [N]: [Title of Decision]

- **Context**: [Brief explanation of the dilemma, constraints, and why a choice is needed now]
- **Options Considered**:
  1. [Option 1]: [Description, pros, cons]
  2. [Option 2]: [Description, pros, cons]
- **Selected / Proposed Direction**: [The recommended or chosen option]
- **Reason**: [Direct technical or business rationale grounded in project constraints]
- **Constraints & Invariants**: [Rules this choice must obey]
- **Affected Workstreams**: [List of workstreams influenced by this choice, e.g., W1, W3]
- **Must Resolve Before**: [Specific task or workstream that cannot start until this is resolved]
- **Risk if Deferred**: [Direct consequence of postponing this decision]
```

## Section B: Task Inventory

Section B organizes the complete inventory of work into coherent workstreams.

### Workstream Naming Contract
- Workstreams represent bounded delivery areas derived directly from the project's actual domain.
- When an upfront gate is necessary (e.g., discovery, specification, architecture consensus), it is designated as `W0` (e.g., `W0 — Architecture & Interface Specification`).
- Do not create boilerplate workstreams (e.g., "Frontend", "Database", "Authentication") unless the project brief actually requires them.
- Format: `## W[Index] — [Workstream Name]`

### Task Format Contract
Every task is an atomic, independently verifiable unit of delivery with a globally unique, continuous number.

```markdown
### [Task ID]. [Action-Oriented Task Title]

- **Workstream**: W[Index] — [Workstream Name]
- **Priority**: P0 | P1 | P2 | P3
- **Purpose**: [1-2 concise sentences explaining what this task accomplishes and why]
- **Dependencies**: [Task IDs that must finish before this task can start, or "None"]
- **Blocks**: [Task IDs that cannot start until this task is completed, or "None"]
- **Deliverable**: [Concrete, observable artifact, code module, configuration, or document produced]
- **Acceptance Criteria**:
  - [ ] [Unambiguous, verifiable condition 1]
  - [ ] [Unambiguous, verifiable condition 2]
- **Verification**: [Specific verification method: unit test, contract test, migration dry-run, benchmark, or smoke test]
- **Risks & Invariants Protected**: [Key invariant maintained or risk mitigated]
```

### Concise Mode (for larger plans)
When presenting plans with many tasks (e.g., >30 tasks), the task inventory can use this concise format while preserving full semantic clarity:

```markdown
### [Task ID]. [Action-Oriented Task Title]
* **Priority**: P[0-3] | **Dependencies**: [IDs or None] | **Blocks**: [IDs or None]
* **Deliverable**: [Concrete deliverable]
* **Acceptance Criteria**: [Key verifiable conditions]
* **Verification**: [Verification method & command/assertion]
```

## Section C: Sequencing

Section C translates task and workstream relationships into an actionable execution sequence, highlighting hard gates, parallel streams, and the critical path.

### Sequencing Format Contract

```markdown
## C. Sequencing

### Gates
- **[Gate Name] (e.g., Architecture Gate W0)**: Downstream implementation cannot start until Tasks [X, Y, Z] are validated.
- **[Integration Gate]**: External vendor/service contract must be finalized before Task [N].
- **[Cutover / Release Gate]**: Final migration dry-run and reconciliation tests must pass before production cutover.

### Execution Flow & Parallelization
```text
[W0]
  ↓
[W1]
  ↓
([W2] ∥ [W3] ∥ [W4])
  ↓
[W5]
  ↓
([W6] ∥ [W7])
  ↓
[W8 — Hardening & Release]
```

### Workstream Dependency Breakdown
- **W0 ([Name])**: Pre-requisite for [Workstreams].
- **W1 ([Name])**: Requires W0. Unlocks W2, W3, W4.
- **W2 ([Name])**: Safe to run in parallel with W3 and W4; depends strictly on W1.
- ...
- **Wn ([Hardening])**: Cross-project regression, security checks, and final operational verification.
```

## Optional: PM Proposals

When the plan will be loaded into project management software (Jira, Linear, GitHub Issues, etc.), append normalized PM creation proposals.

### Workstream Proposal Format
```text
Create workstream
"<Workstream Name>"

Why:
[Cohesive delivery boundary justification]

Impact:
[Unlocks downstream capabilities]
```

### Task Proposal Format
```text
Create task
"<Task Title>" in <Workstream Name>

Priority: P0 | P1 | P2 | P3
Dependencies: [Task IDs]
Deliverable: [Deliverable]

Why:
[Direct purpose]

Impact:
[Downstream impact]
```
